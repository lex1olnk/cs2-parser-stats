# CS2 Parser Stats — Архитектура

Целевое состояние системы после отказа от Docker, перехода на Steam-авторизацию и удаления ПДн.
Соседние документы: [design.md](design.md) — визуальный язык, [plan.md](plan.md) — план работ, [DEPLOY.md](DEPLOY.md) — развёртывание.

---

## 1. Топология

Два Node-процесса и внешняя база. Никаких контейнеров: процессы поднимает pm2 (или systemd), TLS терминирует Caddy либо Cloudflare Tunnel.

```
                      ┌──────────────────────────────────────────┐
   Интернет ─────────▶│  Caddy / cloudflared   (:443)            │
                      └───────────────┬──────────────────────────┘
                                      │ только этот вход публичный
                      ┌───────────────▼──────────────────────────┐
                      │  nextapp (Next.js 15)          :3000     │
                      │  ─ публичные страницы + /admin           │
                      │  ─ API-роуты                             │
                      │  ─ выдаёт и проверяет сессии             │
                      └────┬──────────────────────────┬──────────┘
                           │ localhost, X-Internal-   │ TLS
                           │ Token в обе стороны      │
                      ┌────▼──────────────────┐  ┌────▼──────────┐
                      │ cs-parser (Express)   │  │  Postgres     │
                      │ :3001, bind 127.0.0.1 │  │  (managed)    │
                      │ парсинг .dem          │  └───────────────┘
                      └────┬──────────────────┘
                           │ чтение/запись
                      ┌────▼──────────────────┐
                      │ shared-demos/  (диск) │
                      └───────────────────────┘
```

Ключевое правило: **публично доступен только nextapp**. cs-parser слушает `127.0.0.1` и защищён общим секретом; он не должен быть достижим из интернета ни при каких условиях — он умеет читать файлы с диска и ходить по сети от имени сервера.

## 2. Границы доверия

| Граница | Кто кому доверяет | Чем защищена |
|---|---|---|
| Браузер → nextapp (публичные GET) | никакого доверия | Ничем, данные публичные (статистика турниров) |
| Браузер → nextapp (мутации, `/admin`) | доверие по сессии | Подписанная HttpOnly-cookie + `requireAdmin()` с проверкой по БД |
| nextapp → cs-parser | взаимное | `X-Internal-Token`, привязка к localhost |
| cs-parser → nextapp (`/api/parse/callback`) | взаимное | `X-Internal-Token` + whitelist origin на стороне cs-parser |
| Любой сервис → внешние API (Fastcup/Steam) | одностороннее | Только исходящие запросы на фиксированные хосты |

Что из этого было сломано до текущей итерации: **всё, кроме первой строки**. Админка и все мутации были открыты, callback принимал произвольные «результаты парсинга» от кого угодно, cs-parser принимал произвольные `fileName` (path traversal) и `callbackUrl` (SSRF) при открытом CORS.

## 3. Идентичность и авторизация

### Модель

Три разные сущности, которые легко перепутать:

| Сущность | Что означает | Может ли логиниться |
|---|---|---|
| `User` | Аккаунт Steam: `steamId`, `nickname`, `avatar`. К нему привязана вся игровая статистика | **Да** — это и есть залогиненный пользователь |
| `Profile` | Человек: объединяет несколько `User` (смурфы, второй аккаунт). Используется для капитанства и участия в турнире | Нет, у него нет учётных данных |
| `TournamentParticipant` | Участие конкретного `Profile` в конкретном турнире | — |

После удаления `email` у `Profile` не остаётся ни одного персонального поля — только `name` (игровой ник/позывной, задаётся админом). Идентичность целиком переехала на Steam.

Права администратора живут на `User.isAdmin`, а не на `Profile`: логинится Steam-аккаунт, значит и флаг прав должен быть там же. Бутстрап первого админа — через `ADMIN_STEAM_IDS` в окружении: при логине steamid из списка получает `isAdmin = true`.

### Поток логина (Steam OpenID 2.0)

```
 Браузер            nextapp                     steamcommunity.com
    │                  │                                │
    │ GET /api/auth/steam                               │
    ├─────────────────▶│                                │
    │                  │ ставит state-cookie            │
    │  302 на Steam    │                                │
    │◀─────────────────┤                                │
    │                                                   │
    │ логин на стороне Steam                            │
    ├──────────────────────────────────────────────────▶│
    │                                                   │
    │ 302 обратно: /api/auth/steam/callback?openid.*    │
    │◀──────────────────────────────────────────────────┤
    │                  │                                │
    ├─────────────────▶│ POST openid.mode=check_authentication
    │                  ├───────────────────────────────▶│
    │                  │        is_valid:true           │
    │                  │◀───────────────────────────────┤
    │                  │                                │
    │                  │ GetPlayerSummaries → ник/аватар│
    │                  ├───────────────────────────────▶│
    │                  │                                │
    │                  │ upsert User по steamId         │
    │  302 + Set-Cookie: cs2_session (HttpOnly)         │
    │◀─────────────────┤                                │
```

Верификация обязательно делается запросом `check_authentication` обратно в Steam — параметры в redirect'е подделываются тривиально, доверять им «как есть» нельзя.

### Сессия

Cookie `cs2_session` — компактный HS256-JWT, подписанный `SESSION_SECRET` через Web Crypto API. Почему так, а не серверное хранилище сессий:

- **Без новых зависимостей** — Web Crypto есть и в Node, и в Edge-runtime; не нужен ни `jose`, ни `next-auth`.
- **Без Redis** — сходится с решением «минимум инфраструктуры, без Docker».
- **Работает в middleware** — Edge-runtime не умеет в Prisma, но подпись проверить может.

Атрибуты: `HttpOnly`, `SameSite=Lax`, `Secure` в проде, срок 7 дней.

Двухуровневая проверка прав — намеренно:

1. `middleware.ts` — дешёвый гейт на `/admin/*`: валидна ли подпись и есть ли claim `isAdmin`. Быстро, без БД, отсекает 99% мусора.
2. `requireAdmin()` в самом route handler — **авторитетная** проверка: читает `User.isAdmin` из БД. Нужна потому, что claim в токене может устареть (права отозвали, а токен ещё живой).

Middleware — это удобство и защита страниц; настоящая граница безопасности — guard в обработчике.

## 4. Пайплайн обработки демок

```
POST /api/matches  (requireAdmin)
   │
   ├─ валидация URL (whitelist: cs2.fastcup.net | cybershoke.net)
   ├─ ProcessingSession в БД (прогресс как JSON)
   │
   ├─ download-service: GraphQL/CDN → shared-demos/*.dem|.zip
   │
   ├─ demo-parser-service ──POST /parse-demo + X-Internal-Token──▶ cs-parser
   │                                                                  │
   │                                            parseAllData(demoPath)│
   │                                                                  │
   │◀── POST /api/parse/callback + X-Internal-Token ──────────────────┘
   │
   └─ database-service: транзакция Prisma → Postgres
```

### Второй вход: готовые демки

Если файл уже лежит в `shared-demos` (положен руками, скачан откуда угодно), шаг загрузки пропускается:

```
POST /api/matches/local  (requireAdmin)
   │
   ├─ проверка имени файла (те же правила, что в cs-parser)
   ├─ отсев уже импортированных по ключу local:<имя файла>
   ├─ ProcessingSession
   │
   └─ demo-parser-service → cs-parser → /api/parse/callback → БД
```

Идентификатором матча служит `local:<имя файла>` в `Match.demoPath` — так импортированное отличается от скачанного по ссылке и не импортируется дважды.

Важное отличие: **такой файл не удаляется после разбора**. Скачанное приложением оно чистит за собой, а положенное человеком — его исходник, а не временный артефакт.

Известное ограничение: nextapp ждёт callback поллингом `ProcessingSession` в цикле внутри HTTP-хендлера (по умолчанию до 5 минут, `PARSE_TIMEOUT_MS`). Это работает на постоянно живущем процессе (pm2/systemd) и **не работает на serverless** — функция будет убита по таймауту раньше. Поэтому либо nextapp живёт как обычный процесс на VPS, либо пайплайн переезжает в очередь заданий. Смешанный вариант (Vercel + этот цикл) сломается неочевидным образом, поэтому `vercel.json` из репозитория убран.

## 5. Данные

```
Match ──▶ MatchMap ──▶ Round ──▶ MatchKill / MatchDamage / MatchGrenade
                                  MatchClutch / MatchBlind / MatchPlayerEconomy
Match ──▶ MatchTeam ──▶ MatchMember ──▶ User ──▶ Profile
Tournament ──▶ TournamentTeam ──▶ TournamentParticipant ──▶ Profile
```

Агрегаты считаются материализованными вьюшками на гранулярности «игрок × матч», а не на лету — иначе лидерборд по турниру превращается в полный скан таблиц событий:

| Вьюшка | Что отдаёт |
|---|---|
| `kill_stats_per_match` | `kills`, `hs_kills` |
| `death_stats_per_match` | `deaths` |
| `assist_stats_per_match` | `assists` |
| `damage_stats_per_match` | `damage` (нормализованный, для ADR), `damage_real`, `hits` |
| `rounds_played_per_match` | `rounds` |
| `kast_per_match` | `kast_rounds`, `total_rounds` |
| `player_rating_components_per_match` | компоненты рейтинга: убийства, смерти, выжившие и мультикилл-раунды |
| `match_kill_with_trade` | все убийства + флаг `is_tradekill` (гранулярность — убийство, а не игрок) |

У агрегатов по игрокам есть `tournament_id` — фильтр по турниру не требует join'а с `match`.

**Все вьюшки заводятся миграциями.** Раньше шесть из семи существовали только как SQL, выполненный руками на боевой базе: код на них ссылался, а на свежей базе страницы падали с `relation does not exist`. Любой новый агрегат должен появляться миграцией, иначе окружения расходятся молча.

Вьюшки не обновляются сами, поэтому пайплайн загрузки пересчитывает их сам — один раз на всю пачку матчей, в конце (`stats-refresh-service.ts`). Если данные попали в базу мимо пайплайна, есть `POST /api/stats/refresh` и ручная команда в [DEPLOY.md](DEPLOY.md).

Raw SQL допустим только через тегированные шаблоны Prisma (`prisma.$queryRaw\`... ${value} ...\``) — они параметризуются. Конкатенация строк в SQL запрещена.
Динамические имена полей (сортировка, фильтры) идут через явный whitelist, а не подставляются из query-параметров.

## 6. Окружение и секреты

| Переменная | Сервис | Назначение |
|---|---|---|
| `DATABASE_URL` | nextapp | Postgres |
| `SESSION_SECRET` | nextapp | Подпись сессионной cookie |
| `STEAM_API_KEY` | nextapp | Ник и аватар через Steam Web API |
| `ADMIN_STEAM_IDS` | nextapp | Бутстрап админов, steamid64 через запятую |
| `APP_URL` | nextapp | Публичный origin: return_to для Steam, построение callback-URL |
| `DEMO_SERVER_URL` | nextapp | Где живёт cs-parser |
| `PARSE_TIMEOUT_MS` | nextapp | Сколько ждать ответа парсера, по умолчанию 300000 (5 мин) |
| `INTERNAL_SERVICE_TOKEN` | оба | Общий секрет для служебных запросов в обе стороны |
| `CALLBACK_ORIGIN` | cs-parser | Единственный origin, куда парсеру разрешено слать callback |
| `BIND_HOST` | cs-parser | Интерфейс прослушивания, по умолчанию `127.0.0.1` |

`.env` не коммитится (уже в `.gitignore`), шаблоны лежат в `cs-parser/.env.example` и `nextapp/.env.example`.

## 7. Принятые решения и их цена

| Решение | Почему | Чем платим |
|---|---|---|
| Steam OpenID вместо email/пароля | Аудитория уже в Steam; `steamId` и так канонический ID в парсере; нет паролей — нет их утечки | Зависимость от доступности Steam; нельзя войти без Steam-аккаунта |
| Своя реализация сессии на Web Crypto | Ноль новых зависимостей, работает в Edge, не нужен Redis | Свой код в чувствительном месте; ротация `SESSION_SECRET` разлогинивает всех |
| Отказ от Docker | Compose ссылался на `nextapp/Dockerfile`, а файл назывался `dockerfile` — на Linux сборка падала; изоляция контейнеров реально не использовалась; managed Postgres снимает ops-нагрузку | Окружение на машине настраивается руками — компенсируется `DEPLOY.md` |
| Удаление `Profile.email` | Поле не использовалось по назначению, но хранило ПДн и редактировалось без авторизации | Нет канала связи с игроком вне Steam |
| Общий секрет вместо mTLS между сервисами | Оба процесса на одной машине за localhost | Секрет надо ротировать руками; при разъезде сервисов по машинам понадобится TLS |
